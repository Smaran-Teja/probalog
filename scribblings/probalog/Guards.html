4 Guards🔗

 (require probalog/guards) package: probalog

A guard is the condition under which something holds — for a symbolic set, the condition under which an element is a member. Guards are binary decision diagrams, built through this module on top of the primitives roulette/engine/rsdd exports.

The representation is chosen for canonicality: two guards that mean the same thing are the same object. Or-ing in a disjunct already implied gives back the identical diagram, so a redundant derivation collapses rather than accumulating; equivalence is a comparison rather than a solver call; and a marginal is a weighted count over a diagram that already exists. Building the diagram as the derivation proceeds, rather than compiling an accumulated formula at the end, is the idea of TP-compilation (Vlasselaer, Van den Broeck, Kimmig, Meert & De Raedt, IJAR 2016).

A guard is not a Racket boolean and cannot be branched on. Ask guard-known-true? or guard-known-false? instead, or weigh it with guard-prob.

procedure

(guard-var p) → any/c

  p : (real-in 0 1)
A fresh variable holding with probability p, independent of every other. A p of 0 or 1 gives a constant rather than a variable, so a program with no :: annotations allocates none and every guard in it stays constant.

This is the only way new randomness enters a guard, which is what makes make-base-set the one place the variable order is decided.

Whether two guards hold in exactly the same worlds. Canonicality makes this a comparison rather than a search, which is what the fixpoint loop is built on.

procedure

(guard-known-false? g) → boolean?

  g : any/c
Whether a guard holds in every world, or in none.

These are exact, and are the right way to ask whether an outcome is possible. Because guard-var turns probability 0 and 1 into constants, every variable has probability strictly between them and every satisfying assignment carries positive weight — so a guard has probability zero exactly when guard-known-false? holds of it. Comparing guard-prob against zero is not equivalent: a probability of (- 1 (expt 2 -60)) rounds to 1.0 in a flonum, which would make a possible outcome look impossible.

procedure

(guard-prob g) → real?

  g : any/c
The unnormalised probability that g holds.

Sharp edge: this memoises in each diagram node’s scratch cell and never invalidates, so results are valid only while the weights are unchanged. That holds here — a fact’s probability never changes, and conditioning conjoins evidence rather than reweighting — and it is what makes repeated queries over overlapping guards nearly free.

procedure

(reset-guards!) → void?

Discards the diagram manager and starts over, which is how a fresh program gets a fresh variable space.

This invalidates every existing guard. A guard made before a reset names variables in a manager that is gone, and nothing afterwards can detect that: an operation on one may fault or may quietly return a wrong answer. Callers holding guards across a reset must drop them.

procedure

(add-reset-hook! thunk) → void?

  thunk : (-> any)
Registers thunk to run after each reset-guards!, once the new manager is in place so the thunk may build guards. This is how state holding guards drops what a reset invalidated; the engine uses it to clear accumulated evidence.

(guard-stats)
